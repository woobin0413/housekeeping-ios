# Private photo reservations: implementation status

Status: task 14 is implemented and verified locally. The database reserves immutable object keys, the media function exposes only retry-safe reservation creation, and the private Storage bucket enforces uploader-only unfinished access plus household reads after attachment.

## Implemented boundary

- `reserve_photo` derives identity and household membership from the authenticated session, validates an exact `{householdId, requestId}` input, and returns the same 24-hour reservation for an identical retry.
- Object keys are generated by the server as `<household>/<uploader>/<photo>.jpg`; clients cannot create photo metadata or select a different key.
- `purchase-photos` is private, accepts only `image/jpeg`, and has a 5 MiB bucket limit.
- Storage INSERT requires the uploader's live RESERVED row. There is no UPDATE or DELETE policy, so uploads cannot overwrite objects and ordinary sessions cannot directly remove them.
- Authenticated GET permits the uploader's RESERVED/READY object. It permits either active spouse after the photo is ATTACHED to a nondeleted item. Bucket listing remains hidden, and revocation takes effect on the next request.
- The media route authenticates the bearer token with Supabase Auth, bounds JSON bodies to 4 KiB, returns normalized errors, and never logs tokens or object contents.
